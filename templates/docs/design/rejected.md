# Rejected patterns

What this product has ruled out, and why. Two jobs:

1. **Stop the loop.** A rejected idea with no written reason comes back every few months — from a new teammate, or from an agent that has no way to know.
2. **Anchor "generic".** When a role asks whether a new screen is interchangeable with any other product's, this list is what it compares against. Without it, "this looks generic" is an opinion with nothing behind it.

Record what **you turned down** too — including proposals from a role. A rejection you never wrote down is a rejection the next session will not know about.

## Entry format

Copy this block per rejection:

```
### <what was rejected>

- **Proposed for:** <the problem it was trying to solve>
- **Why rejected:** <the reason — a constraint, a user cost, a conflict with an approved pattern>
- **Do instead:** <the alternative that stands, or "no alternative yet — the problem is open">
- **Rejected:** <date>
```

The **Do instead** line matters more than the rejection. A rejection without an alternative leaves the problem unsolved and invites the same proposal back in different clothes; if there genuinely is no alternative yet, say that explicitly so the problem stays visible.
